# PromQL — how the numbers in the README were derived

Every figure quoted in the README's *What the numbers say* table comes from one
of the queries below. They are written to be pasted straight into Prometheus at
<http://127.0.0.1:9090> (Graph → paste → Execute) or run over the HTTP API:

```bash
curl -s --get http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=<the query>' | python -m json.tool
```

Measurements below were taken over 31 requests generated by
`scripts/seed_traffic.py` against a local instance.

---

## The one thing to get right first

**Use `increase(...[$__range])` for ratios, not `rate(...[5m])`.**

This project's traffic is bursty — a few minutes of questions, then idle. A
`rate()` over a short window returns zero during the idle stretches, and any
average across the whole window is then dragged toward zero. The first version
of the "where does the time go" panel did exactly this and reported a **3.9%**
retrieval share against a true **99.9%** — off by a factor of 25, in the
direction that reverses the conclusion.

`increase(...[$__range])` totals the numerator and denominator across the whole
window, so it is unaffected by how requests are spaced.

Rule of thumb: **rates and quantiles over time → `rate()`. Shares and averages
over a period → `increase()`.**

## 1. Which agent has the highest P95 duration?

```promql
histogram_quantile(
  0.95,
  sum by (agent, le) (rate(agent_duration_seconds_bucket[5m]))
)
```

This is the panel form — it plots P95 as it moves. Pasted into Prometheus as an
*instant* query it returns nothing unless traffic arrived in the last five
minutes, which looks like a broken query and isn't. For a single number over a
window that actually contains the traffic, swap `rate` for `increase` and widen
it:

```promql
histogram_quantile(
  0.95,
  sum by (agent, le) (increase(agent_duration_seconds_bucket[6h]))
)
```

| Agent | P95 | Mean | Max |
|---|---|---|---|
| `orchestrator` | 2.45 s | 2.61 s | 6.50 s |
| `sql_agent` | 2.05 s | 2.14 s | 2.90 s |
| `synthesis` | 1.96 s | 1.95 s | 2.85 s |
| `rag_agent` | 0.65 s | 0.71 s | 0.98 s |

`sum by (agent, le)` is the part that matters: `histogram_quantile` needs the
`le` label intact, so the aggregation has to keep it and only collapse the
labels you actually want gone.

**Read this one with care at n=31.** A P95 over a handful of observations is
dominated by one or two slow calls — here, the orchestrator's cold start. The
ranking is believable; the absolute values are not yet.

## 2. For the SQL agent, how much is database time vs model time?

`sql_query_duration_seconds` is nested inside `agent_duration_seconds{agent="sql_agent"}`,
so dividing one by the other gives the share directly.

```promql
sum(increase(sql_query_duration_seconds_sum[$__range]))
  /
clamp_min(sum(increase(agent_duration_seconds_sum{agent="sql_agent"}[$__range])), 0.001)
```

**Result: 2.6% database, 97.4% model.**

The same shape for the RAG agent:

```promql
sum(increase(retrieval_duration_seconds_sum[$__range]))
  /
clamp_min(sum(increase(agent_duration_seconds_sum{agent="rag_agent"}[$__range])), 0.001)
```

**Result: 99.9% retrieval.**

`clamp_min` guards the denominator: with no traffic in the window both sides are
zero, and `0/0` renders as `NaN` rather than a flat line.

These two are the most useful numbers the whole exercise produced, because each
cancels an optimisation that looked obvious:

- The database was the natural suspect for SQL latency. It accounts for 2.6% —
  indexes, query tuning, and connection pooling would move nothing.
- `TOP_K` and ChromaDB were the natural suspects for retrieval latency. The node
  spends essentially all of its time on the Voyage embedding round-trip; local
  vector search over ~240 chunks is sub-millisecond.

## 3. What is the input/output token ratio per agent?

```promql
sum by (agent) (increase(llm_tokens_total{type="input"}[$__range]))
  /
clamp_min(sum by (agent) (increase(llm_tokens_total{type="output"}[$__range])), 1)
```

| Agent | Ratio | Why |
|---|---|---|
| `orchestrator` | **22.4** | Fixed system prompt plus a tool schema in; a two-token routing decision out |
| `synthesis` | 5.8 | Retrieved chunks and SQL rows in; a short grounded answer out |
| `sql_agent` | 4.8 | Schema and rules in; one SELECT out |

The orchestrator's ratio is the actionable one. A high ratio against a prefix
that never changes is the textbook case for prompt caching — the cached portion
bills at roughly a tenth of the input rate.

## 4. What does one average question cost?

`orchestrator` runs exactly once per question, so its execution count is the
question count.

```promql
sum(increase(llm_cost_usd_total[$__range]))
  /
clamp_min(sum(increase(agent_requests_total{agent="orchestrator"}[$__range])), 1)
```

**Result: $0.0023 per question** — about **$2.33 per thousand** on Haiku 4.5,
across all three model calls.

Per-agent breakdown:

```promql
sum by (agent) (increase(llm_cost_usd_total[$__range]))
```

Cost is recorded as its own counter rather than derived in PromQL, so the panel
is a plain `sum()` and the pricing table lives in one place
([`metrics.py`](../metrics.py)). The trade-off is that a model missing from
`MODEL_PRICING` records tokens but no cost — which is why there is an alert for
exactly that condition.

## Supporting queries

**Refusal rate** — refusals are designed behaviour, so this is a drift detector,
not an error rate:

```promql
sum(increase(refusals_total[$__range]))
  /
clamp_min(sum(increase(agent_requests_total{agent="synthesis"}[$__range])), 1)
```

**Chunks per retrieval** — sits at `TOP_K` (4) in normal operation; a drop toward
zero means the index is missing or was built with a different embedding model:

```promql
rate(retrieval_chunks_sum[5m]) / clamp_min(rate(retrieval_chunks_count[5m]), 0.001)
```

**A model recording tokens but no cost** — the signature of a model id absent
from `MODEL_PRICING`:

```promql
sum by (model) (rate(llm_tokens_total[30m])) > 0
  unless
sum by (model) (rate(llm_cost_usd_total[30m])) > 0
```

**Error rate per agent:**

```promql
sum by (agent) (rate(agent_errors_total[5m]))
  /
clamp_min(sum by (agent) (rate(agent_requests_total[5m])), 0.001)
```

## Gotchas worth knowing

| | |
|---|---|
| **`$__range` is Grafana-only** | Prometheus itself does not know it. Substitute a literal window (`[6h]`) when querying the API directly. |
| **Counters only go up** | `llm_cost_usd_total` is cumulative since process start. Wrap it in `increase()` or `rate()` for anything time-bounded; the raw value answers "since when?", not "recently". |
| **Histogram quantiles need `le`** | `sum by (agent) (...)` drops `le` and breaks `histogram_quantile`. Always `sum by (agent, le)`. |
| **`_sum / _count` is a mean, not a quantile** | Useful, but it hides the tail — which is the part that matters for latency. |
| **A restart resets everything** | These are in-process counters with no persistence. `increase()` handles counter resets correctly; reading raw values across a restart does not. |
